# mmdb 上下文内核：技术方案

状态：实现说明 v0.6，2026-09-09。S1 内核及 S2 至 S4 所需的流式历史、检查点、当前依赖验证和业务动作已实现；首轮真实任务驱动的 checkpoint 生命周期修正见下文及 [MiuMiu 质量验收](../../miumiu/docs/CONTEXT-ACCEPTANCE.md)。旧数据不迁移，从新格式目录开始。产品依据见 [Feature Doc v1.0](FEATURES.md)。

## 推荐方向

沿用原生 `MemoryDatabase` 的持久化、版本、来源和操作回执机制，将其演进为所有 harness 共用的上下文入口。完整历史、ontology 内容、关系与检查点由 mmdb 管理；harness 通过这个入口读写上下文，继续拥有任务执行与工具权限。

S1 提供一个最小可用场景：独立 Rust harness 定义领域对象和关系，保存原始交互及带来源的对象，关闭并重新打开数据库，然后按引用、词项和显式关系找回它们。可运行示例见 [context_harness.rs](../crates/mmdb/examples/context_harness.rs)，无需模型服务。

现有文档要求显式裁决后才激活语义提案。Feature Doc 已确认自主保存后可召回，技术方案据此新增正式的 agent 写入路径，保留结构、来源及版本校验；不借用 `Actor::User` 伪装 agent 写入。

## 模块职责

对外通过 `MemoryDatabase::context` 返回 `ContextStore`，内部实现位于 [context 模块](../crates/mmdb/src/context/mod.rs)。它复用原生数据库的 keyspace、写锁、同步批次、存储身份与租约。

| 模块 | 隐藏的复杂性 | 对外可观察结果 |
| --- | --- | --- |
| `catalog.rs` | 定义去重、名称冲突、类型版本和属性校验 | 应用与 agent 能发现、复用和扩展类型 |
| `history.rs` | 会话顺序、稳定事件身份、完整载荷、调用关联及清理 | 任意历史引用都能读取原记录或明确的不可用状态 |
| `records.rs` | 对象、关系、来源、推断身份、当前状态和历史修订 | 写入后的内容可持续引用、修正并参与召回 |
| `search.rs` | 范围过滤、词项候选、关系扩展、原文搜索与预算 | 返回带来源、版本和关联路径的有限结果 |
| `checkpoints.rs` | 历史位置、父检查点及可用性 epoch 的提交检查 | 只有原文和引用仍有效的检查点可恢复 |
| `actions.rs` | 动作版本、对象及输入检查、准备与终止状态的幂等提交 | harness 可关联实际结果；定义不获得执行权限 |
| `storage.rs` 与原生内核 | 租约、写入串行化、幂等回执、批次提交及载荷校验 | 成功回执表示内容与必要索引已持久保存 |

所有派生索引指向 mmdb 的记录引用及版本。一个对象只有一个权威记录，索引中的副本可以重建。首阶段使用词项和显式关系索引；向量索引的接入由后续验收结果决定。

把现有两个数据库直接并排封装，会把记录映射、重复写入和一致性修复留给调用方，因此不推荐作为主方案。复用多模型能力时，应复用其内部检索实现，并在 mmdb 内部完成记录和版本映射。

## 身份、类型与来源

| 概念 | 推荐约束 |
| --- | --- |
| 记录引用 | 携带存储身份、记录族及记录 ID；延续原生引用区分记录族的规则，避免跨族 ID 混淆 |
| 版本引用 | 在稳定记录引用上固定 revision；历史证据和检查点使用固定版本，读取当前状态显式选择 head |
| 用户归属 | 每条记录有明确 owner，默认共享范围是该用户；从 harness 的可信调用上下文取得，模型不能在内容中自行改写 |
| Session 与 agent | 保留 harness 提供的稳定身份作为来源；切换模型窗口不分配新 session |
| 类型定义 | 对象类型、关系类型均有稳定身份、名称和不可变的版本；实例固定创建或更新时使用的类型版本 |
| 内置类型 | 提供可选的 `TypeDefinition::note(scope)`，名称为 `mmdb.note`；调用方通过普通 `define_type` 注册，通过 `find_type`、`list_types` 发现。创建句柄不自动写入类型 |
| 领域类型 | 初版使用有界的属性定义，支持文本、布尔、整数、有限浮点数、时间、记录引用及这些值的列表；必填属性、引用目标类型及未知属性均校验 |
| 关系 | 固定关系类型版本、两端记录引用及依据；新增关系与端点校验处于同一次写入操作 |
| 来源 | 保存原始历史或既有证据的版本引用、来源 agent、session 及运行标识；推断身份随读取和召回保留 |

初版的类型演进采用新增版本：修改属性定义或关系端点约束会产生新版本，已有实例继续使用原版本。更新实例时显式选择目标版本并重新校验，不批量隐式改写旧实例。同一 owner 和名称下，相同定义返回已有定义，不同定义报告冲突；新版本必须带预期 revision。

普通 agent 写入经校验即可成为可召回的上下文。历史观察、推断与用户明确指示保留不同身份；可召回表示这条信息已保存并可使用，不表示 mmdb 已证明其内容真实。

S1 的 `ContextAccess` 由可信 harness 提供 owner、actor 和允许范围，默认范围为当前 owner 的 `Personal`。来源 agent、session、run 不产生隐式隔离。记录引用包含 owner、存储 era、记录族和 ID；固定版本另带 revision，跨 owner 或 era 的引用会被拒绝。

常规召回要求记录及来源均为当前有效版本。来源修订或撤回后，旧的派生内容停止参与日常召回，调用方可以基于新来源重新修订；显式历史读取仍可核对旧版本。修订不能直接或间接把自身作为来源。清除来源后，依赖它的载荷也不可展开；`inspect_header` 保留状态与来源元数据用于解释。

## 统一接口的操作约束

S1 的公开请求与响应类型见 [types.rs](../crates/mmdb/src/context/types.rs)。以下操作均已实现；业务执行与模型窗口管理仍由 harness 承担。

| 操作 | 输入要点 | 成功结果与失败语义 |
| --- | --- | --- |
| `define_type`、`revise_type`、`find_type`、`list_types` | 调用范围、类型定义或引用、预期版本、操作 ID | 返回类型版本；名称冲突、版本冲突及不合法定义分别报告 |
| `append_history` | session、来源事件 ID、预期历史位置、`Read` 载荷、工具调用关联、操作 ID | 返回稳定引用及新历史位置；同一事件同内容重试返回原结果，同身份不同内容拒绝 |
| `save_object`、`revise_object`、`save_relation`、`revise_relation` | 类型版本、属性、来源、推断身份、预期记录版本、操作 ID | 返回记录及版本；写入成功后可参与召回，过期版本不会覆盖新内容 |
| `relations`、`recall` | 当前需求、已知引用、允许范围、有效时间、结果与扩展预算 | 关系支持方向与类型筛选、游标分页；召回返回内容、版本、来源、关联路径及截断状态 |
| `head`、`inspect_header`、`read`、`read_payload` | 稳定引用或固定版本、载荷读取范围 | 返回对应头或版本，超大载荷分页读取；读取不会向历史追加副本 |
| `history_position`、`history`、`search_history` | session、已读位置，或原文查询、游标与扫描预算 | 连续历史分页与原文匹配；原文命中返回固定引用及字节位置 |
| `retract`、`purge`、`recover_payloads` | 预期版本、操作 ID，或清理预算 | 撤回、清除及有界载荷清理；清除和修改原始历史要求可信的 User 或 Operator 身份 |
| `operation_receipt` | 原操作 ID | 查询是否有已提交回执，用于恢复提交结果不确定的操作 |
| `save_checkpoint`、`latest_checkpoint`、`latest_run_checkpoint` | Session/Run 范围、session、run、历史位置、预期父版本与可用性 epoch、来源、载荷、操作 ID | 各范围独立检查父版本；子运行不得写入 Session 检查点；未提交位置、过期父版本和失效来源被拒绝 |
| `define_action`、`revise_action`、`find_action`、`actions_for` | 作用类型、输入类型、前置条件和来源 | 返回固定动作版本或按对象分页发现；模型定义不创建工具绑定 |
| `prepare_action_once`、`finish_action` | 动作与对象版本、输入、harness 执行身份、结果和来源 | 只有准备操作的获胜者可调度；重试读取既有状态；mmdb 不调用工具 |
| `validate_current`、`availability_epoch` | 最多 64 个固定引用及可选有效时间 | 检查当前 head、可用性及传递依赖；历史 `read` 与当前有效性校验分别使用 |
| `history_sessions`、`tool_history` | 有界 session 游标或 session 与调用 ID | 为可信 System/Operator 恢复提供历史目录及精确调用关联 |

对照同一操作 ID 的内容摘要保存回执，重试时先核对回执。若底层提交结果不确定，应报告可按操作 ID 查询的状态；调用方查询或使用原 ID 重试，不为同一动作生成新的写入身份。

操作内容摘要包含可信调用身份和来源；恢复写入时需保留原请求、operation ID 及 provenance。事件去重另行忽略预期历史位置，因此在后续事件已写入后重试同一原始事件，仍返回原来的引用与序号。回执只证明原操作提交过，读取载荷仍检查当前清除状态。

## 连续历史与持久化

每个 session 有一个单调递增的逻辑序号。历史事件保存稳定事件 ID、序号、事件种类、来源运行及完整载荷引用。序号由 mmdb 在写入串行化区间内分配，时间戳只描述时间，不承担唯一排序。

历史支持用户消息、assistant 开始／有序片段／终止、工具调用与结果及通知。每次追加提交一个完整事件，片段与终止记录共享稳定消息 ID；工具结果要求同一 session 已有唯一调用。`HistoryInput.sources` 为复制或整理的上下文快照登记来源依赖，独立原始观察可以不带外部来源。

原始快照可引用仍可读取的类型定义或历史修订，来源不必是当前 head；常规对象和动作写入仍要求当前有效依赖。来源清除对历史副本同样生效。所有来源共享单次深度与数量预算，并计入新记录本身，避免提交成功后立即因深度超限而不可读取。

`ToolResult` 与前置调用也按历史可读性关联。调用执行期间修订其已读取的来源，不会阻止结果落盘；清除来源或使关联消息不可用仍会阻止读取和新增依赖。工具是否可以执行，继续由当前对象、动作及 harness 权限检查决定。

同一批次提交事件头、历史位置、必要的查询索引及幂等回执。大载荷按有界块写入，完整载荷确认后再发布引用；未完成的块有独立状态，不得作为完整记录返回。实现需要流式读写和内容校验，不能用当前证据文本上限截断原始历史。

S1 的原始历史搜索按历史键序扫描完整载荷，使用可持久化游标限制每次扫描的事件数与字节数。它支持跨载荷块和查询页的子串匹配，ASCII 忽略大小写，中文按原始 UTF-8 字节匹配；每个命中事件返回首个匹配位置。跨 session 查询按 session 键序遍历，单个 session 内按逻辑序号遍历。

日常上下文召回使用词项索引和显式关系扩展，中文采用单字及相邻双字词项。S1 原文搜索的代价随扫描内容增长，后续可以增加原文索引；当前完整性验收覆盖超过 2 MiB 的原文、跨页中文匹配和末尾未整理的信息回查。

载荷块为 32 KiB，每个块校验摘要，单次载荷读取最多 1 MiB。结构化对象和类型定义最多 128 KiB，来源最多 64 条。默认召回最多返回 12 项；候选、关系边、深度与结果均有上限，原文查询最多扫描 16 MiB。来源依赖检查限制深度 32、每次最多访问 4096 项，超过边界明确报错。

首阶段采用嵌入式独占写入，一个数据目录同时由一个 `MemoryDatabase` 持有。共享演示是两个 harness 顺序重开同一目录，同进程内可共享数据库句柄。流式载荷写入期间持有写锁，harness 应提供可结束的输入流，避免长时间阻塞同库其他操作。

检查点固定历史位置，并保存恢复需要的记录引用。检查点中整理出的内容也记录来源依赖，来源被清除时，相应派生载荷不能继续展开。模型恢复只是读取检查点及其后的历史，不重新追加已存在的消息。记录读取、搜索和关系扩展都要检查 owner、作用域、版本及可用状态。

Session 与 Run 检查点具有独立索引和父版本比较。harness 通过 `ContextAccess.parent_run` 标明嵌套来源，子运行只能更新自己的 Run 检查点，不能替换整个会话的恢复入口。

当前仓库锁定 fjall 2.11.2，已有代码使用带 `SyncAll` 的批次。该版本提供跨 partition 的原子批次与只读快照，可用于这里的单库事务；两个独立数据目录之间仍需要应用层恢复协议。[fjall 2.11.2 官方文档](https://docs.rs/fjall/2.11.2/fjall/)

## 第一阶段 S1：可独立使用的上下文内核

S1 的交付范围是 mmdb 内的类型目录、带来源对象、显式关系、完整历史、稳定读取和有界基础召回。它可由独立 Rust harness 使用，miumiu 可以继续运行现有入口。业务动作的执行集成和自动窗口切换归后续阶段。

为保持阶段可独立合并，S1 新的上下文格式通过显式入口创建和打开，现有 v1 格式和调用入口继续可用。统一契约只面向新格式提供完整能力；旧格式不能在一次普通 open 中被隐式升级。后续接入完成后再收敛兼容入口。

| 检查项 | 文件位置与实施内容 | 验收证据 |
| --- | --- | --- |
| S1-01 | 在 `crates/mmdb/src/context/` 拆分接口类型、类型目录、历史、对象关系、存储及召回模块；由原生内核提供批次和来源校验 | 一个调用方可以通过统一入口完成下面各项，无需同时创建 `Database` |
| S1-02 | 调整 `crates/mmdb/src/native_memory.rs`、`crates/mmdb/src/lib.rs`，复用 `store_format.rs` 的现有 reset 接口，提供显式格式入口与共享事务机制 | 错误格式拒绝打开；reset 后新 era 不解析旧引用；旧目录保留在隔离位置 |
| S1-03 | 实现带版本的类型目录及对象写入，内置与自定义类型使用同一发现方式 | research 定义对象后，另一个 harness 能发现定义、保存实例并读取来源 |
| S1-04 | 实现有序历史、幂等追加、完整载荷读取及来源引用 | 重启后字节一致；并发同 session 写入不产生重号；重复提交不产生重复事件 |
| S1-05 | 实现关系端点校验、邻接索引、中英文词项候选及有界召回 | 查询可找出只通过显式关系连接的记录，范围过滤、有效时间和修订状态有效 |
| S1-06 | 新增 `crates/mmdb/tests/context_contract.rs` 和 `crates/mmdb/examples/context_harness.rs` | 两个最小 harness 在相同允许范围下顺序打开同一数据目录，复用类型、记录及历史引用 |

S1 的代码集中在 mmdb crate，未增加依赖、服务或新的语言运行时。公开入口是 `MemoryDatabase::create_context`、`open_context` 和 `context`，外层格式为 `mmdb-context-v1`。检查点和业务动作沿用同一格式与原生事务边界，不增加外部服务。

## 分期顺序

| 阶段 | 可独立交付的能力 | 与下一阶段的关系 |
| --- | --- | --- |
| S1 上下文内核 | 独立 harness 可保存、查询和回溯领域上下文 | 无需 miumiu 改造也可使用 |
| S2 MiuMiu 历史与自主保存 | 当前会话及原始工具记录使用统一入口，agent 保存内容后可召回 | 已改善新任务和新 session 的上下文复用，不依赖自动窗口切换 |
| S3 窗口连续执行 | 检查点、有限工作上下文、同 session 恢复及单条历史链 | 普通聊天与长任务均可使用，不依赖工作流改造 |
| S4 动态工作流 | 业务动作描述与执行衔接，上下文参与规划，运行中重规划，模板版本与运行计划分别演进 | 使用前面已经可用的数据与恢复能力 |

S2 至 S4 的应用侧流程和文件位置见 [MiuMiu 技术方案](../../miumiu/docs/CONTEXT-DESIGN.md)。

## 数据兼容与恢复

2026-09-08 已确认：旧数据不迁移，从 reset 后的新目录开始。实现不包含旧记录转换、旧引用映射或双写迁移流程。

reset 沿用现有租约、格式校验和可恢复的隔离重置机制。新目录取得新的存储身份，旧引用不能在新目录中意外解析；普通 open 不自动清空旧目录。实现与验收使用临时目录；MiuMiu 普通启动使用新的版本目录，不隐式重置已有用户目录。

重建召回索引不改变原始历史，harness 的清屏或 undo 也不删除原文。显式上下文整库 reset 覆盖原始历史、ontology 内容和检查点，旧目录进入隔离位置；harness 保留执行身份与效果状态，并使旧 era 的内容缓存和待提交意图失效。

## 验证与主要风险

统一内核验证命令在 mmdb 根目录执行：

```sh
cargo fmt --all --check
cargo test -p mmdb --test context_contract
cargo run -p mmdb --example context_harness
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
git diff --check
```

新增接口测试位于 [context_contract.rs](../crates/mmdb/tests/context_contract.rs)。[内核故障测试](../crates/mmdb/src/context/tests.rs) 另行注入持久提交后的确认丢失及载荷损坏；两项均通过公开读取与恢复行为断言。

这些验收使用临时数据目录和确定性模型 fixture，不使用真实领域数据或 API key。应用 HTTP 测试仅监听 localhost；没有执行真实用户数据 reset。隔离副本排除了原先已有的桌面和传输层工作。

必须覆盖持久化重开、不同用户范围、同 session 并发追加、同操作重试、同身份不同内容、旧版本更新、非法关系端点、关系循环、预算耗尽、超大原文、部分载荷写入、来源被清除以及提交结果不确定的恢复。测试通过统一接口断言可观察结果，避免只检查内部索引是否写了某个键。

最脆弱的假设是：原生的固定记录族可以在保留来源和清除语义的前提下扩展成领域类型。如果扩展迫使同一内容在两个模型中长期双写，应把相应存储逻辑下沉为共用内核，再继续增加接口。S1 的独立 harness 验收用于尽早发现这个问题。

资源风险主要在完整历史与关系扩展。载荷读写必须分块，召回必须接受显式上限；索引损坏或重建时，稳定引用读取仍有独立可用路径。首阶段沿用现有依赖，不要求 API key、第三方账号或 embedding 服务。

## S2 至 S4 的内核边界

检查点保存不可变载荷、父检查点、session/run、历史位置和来源引用。生成开始前捕获的可用性 epoch 必须在提交时仍有效。修订、撤回或清除会推进 owner 的可用性 epoch；旧检查点不能用于当前恢复。

历史读取另外检查载荷脱敏 epoch：普通修订允许旧检查点及其派生原文继续按 pin 审计，避免已经发生的工具调用因源版本变化而无法保存完成结果。任意记录清除、任意历史事件撤回都会推进脱敏 epoch，较早检查点的历史载荷不可再读，包含未单独列出的摘要输入。marker 同时记录对应的可用性 epoch；marker 缺失或与当前 epoch 不一致时，按旧 writer 可能已执行清除处理，保守采用当前 epoch，不复活旧摘要。这两个 epoch 在同一持久批次更新。

`latest_checkpoint` 返回定位用 header，不保证该检查点当前有效。harness 恢复前必须使用 `validate_current`；`current_state` 只表示记录自身的 head 状态，不能替代传递依赖校验。assistant 的任一片段不可用时，聚合消息和其他片段读取也不可用，避免复制的终止消息重新暴露原文。

动作描述使用有界输入属性与 `exists`、`equals` 前置条件，`equals` 值必须匹配对象属性类型。准备动作检查当前动作、目标对象、有效时间、传递来源及参数；同一身份并发准备只有一个调用方取得首次调度权。执行状态包括 Prepared、Succeeded、RejectedBeforeDispatch、FailedNoEffect 和 EffectUnknown。实际执行事实要求 System/Operator 身份，普通 agent 不能伪造或撤回执行事实。

S2 至 S4 的应用入口与运行恢复见 [MiuMiu 实现说明](../../miumiu/docs/CONTEXT-DESIGN.md)。2026-09-09 独立原生程序实际打开 MiuMiu 的公开任务数据库：`inspect_context_quality` 检查历史、工具配对、载荷、来源和 checkpoint 链；`verify_context_lifecycle` 在副本上核对关系命中、动作事实、作用域、预算、修订和清除后重开。完整报告见[真实任务质量验收](../../miumiu/docs/CONTEXT-ACCEPTANCE.md)。

本轮隔离 `cargo test --workspace --offline --locked` 通过，包括 189 项 mmdb 库测试、31 项 context 契约测试及其余 workspace 测试；fmt 和严格 workspace all-targets Clippy 通过。确定性边界测试与实际领域样本分别记录，不外推为一般召回准确率或规划质量保证。
