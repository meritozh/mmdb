# 连续会话日志与原文搜索

可信 harness 把一个会话的用户消息、assistant 消息、工具调用与结果和通知按序追加到会话日志，之后可以翻页、搜索原文、固定版本并作为新对象的来源。即使 agent 当时没有整理某段交互，重置记忆后这段日志仍完整可读。

Status: shipped

## Behavior

- Who: 可信 harness，以 `ContextAccess` 提供 owner、actor、scope 和来源 agent、session、run。
  - access 绑定了 session 时，只能追加该会话的事件。
  - 用户消息只能由 User、System 或 Operator 写入；列出会话需要 System 或 Operator；撤回或清除日志事件需要 User 或 Operator。
  - 重置记忆由持有存储租约的进程发起，凭计划的确认摘要提交。
- Entry: `Store::create(path)` 创建存储，`Store::open(path)` 重开，再以 `store.session_log(access)` 取得会话日志句柄，[检查点](context-checkpoints.md)也在这个句柄上。句柄上的方法名使用术语表的词，不带 history。
- Does: 会话日志和检查点存放在会话模块，与记忆模块同在一个存储，共用租约和批次提交。切换模型窗口仍追加到原会话的日志。MMDB 在写入时分配单调递增的序号，时间戳描述事件时间。
  - 追加：接受稳定事件 ID、可选预期位置、输入流及来源。完整写入后，事件头、序号、索引和回执一起发布。同一事件同内容重试会取回原序号，即使后面已经追加其他事件；同一身份提交不同内容会冲突。
  - 消息：assistant 的开始、有序片段和终止事件共用消息 ID。撤回或清除其中一个事件后，整条消息及其余片段都不能再用来重现原文。工具结果必须关联同一会话中唯一的调用；调用不可读时，结果也不可读。
  - 来源：日志事件可以把记忆模块中的记录作为来源，对象和关系也可以把日志事件作为来源。追加时来源必须可读；复制可读的旧修订时登记来源，独立观察可以不带外部来源。日志事件写入后只读：能否读取只取决于它自己、所在的消息和关联的工具调用，来源之后的修订、撤回、清除或重置都不改变它。读取时仍需要追加时各来源所在的 scope，复制不会放宽可读范围。当前可用性检查照常沿来源跨模块进行。要从历史中抹掉内容，就清除那条日志事件，以它为来源的对象、关系和检查点随之不可用。
  - 读取：按日志位置定位和翻页，按 pin 读取载荷，列出会话，为恢复取得工具调用与结果的配对。恢复时读已有日志，只追加新产生的交互。
  - 搜索：返回匹配事件的固定引用、首个匹配的字节位置和续查游标。跨会话按键序、同会话按序号遍历，子串可以跨存储块和查询页。ASCII 匹配忽略大小写，中文按 UTF-8 字节匹配。未命中且仍有游标时可以继续扫描。
  - 重置记忆：先取得计划，计划给出要重置的记忆模块、新旧 era、过期时间和确认摘要，再凭完整摘要提交。一次提交让记忆模块换新 era，旧记录立刻不可见；磁盘空间由有上限、中断后能接着做的清理回收，不留隔离副本。记忆模块包括原生记忆，以及领域上下文的类型、对象、关系、业务动作定义与执行记录。会话模块不受影响。
  - 重置记忆之后：日志事件和载荷照常可读，指向旧记忆的来源显示为已重置。这些事件在当前可用性检查中也照常可用：指向旧记忆的来源是检查的终点，不阻断检查，直接引用旧记忆本身才报已重置。重置前保存的检查点载荷仍可读，但不能用于当前恢复，harness 从它记录的日志位置重新生成。
  - 整库重置：旧目录移到隔离路径，所有模块换新 era。
- Fails:
  - 重置记忆之前的记忆引用读作不可用：已重置，与已清除区分。另一 owner 或另一存储的引用被拒绝访问，整库重置之前的引用也算另一存储。
  - 追加中断不推进日志位置，`recover_payloads` 有界清理未完成的载荷。
  - 重置记忆要么整体生效，要么没有发生；没做完的清理在下次打开时继续。确认摘要不符或计划过期时不做任何改变。
  - 旧格式的目录，包括 `mmdb-context-v1`，打开时被拒绝，需要整库重置，不做迁移。
- Limits: 载荷按 32 KiB 分块并校验摘要。单次读取载荷最多 1 MiB。单次搜索最多扫描 4,096 个事件或 16 MiB。读取输入流期间持有存储的写锁，长时间不结束的流会阻塞同一存储的其他写入。
- Keeps: 日志事件、载荷和检查点保留到被清除或整库重置，重置记忆不影响它们。旧记忆的分区由清理删除，不留隔离副本；最近写入的内容还留在存储引擎共用的预写文件里，等它轮转后才释放，所以重置记忆不是安全擦除。

## Decisions

### 会话日志是同一存储里的独立模块

会话日志和检查点放进会话模块，与记忆模块同在一个存储。会话日志是交互的唯一来源，重置记忆后重建记忆正需要它；同一存储让清除、可用性 epoch 和记录变更同批提交，运行状态之后也能与日志追加同批提交。

- Rejected: 维持日志和检查点随记忆一起重置，在操作者重置记忆就是要清空一切时更好；把日志放进独立目录，在日志与记忆之间永远不需要同批提交时更好。
- Wrong-call signal: 跨模块的可用性检查无法单向分层，必须读懂记忆模块的内部格式。

### 日志写入后只读

日志事件能否读取只取决于它自己、所在的消息和关联的工具调用，来源之后的修订、撤回、清除和重置记忆都不改变它。会话日志记录当时发生的交互，模型当时读到的记忆已经成为这段交互的一部分。原文通常本来就在用户消息或工具结果里，只清除记忆从来抹不干净历史；要抹掉，就清除日志事件本身，派生自它的对象、关系和检查点随之不可用。派生数据跟随来源，日志不跟随记忆，所以重置记忆既不会让日志失效，也不会让重置前的清除失效。

- Rejected: 清除记忆对象时，让复制了它的日志事件一起不可读，在记忆常常是某段内容在存储里唯一的副本时更好。
- Wrong-call signal: 用户清除一条记忆后，要求它的内容同时从会话日志消失，而逐条清除日志事件做不到。

### 入口是不以记忆命名的存储

`Store` 打开存储，再分别取得会话日志、领域上下文和原生记忆的句柄。继续用 `MemoryDatabase` 打开，等于让记忆拥有会话模块，与这次划出的重置边界相反，运行状态和记忆迁入时还要再改一次入口。

- Rejected: 在 `MemoryDatabase` 上挂会话日志句柄，在记忆始终是会话之外唯一的模块时更好。
- Wrong-call signal: `Store` 只剩转发调用，没有自己的行为。

### 只重置记忆时原地换 era

一次提交给记忆模块换新 era，旧记录由有界清理回收，不留隔离副本。同一个 keyspace 无法像目录那样整体改名隔离，复制副本要扫描整个记忆模块；隔离目录防的是重置错路径，而模块重置发生在受管存储内部。项目处于 startup，允许丢弃数据。

- Rejected: 先把记忆模块导出到隔离目录再换 era，在误重置经常发生、或操作者确实会从副本找回记忆时更好。
- Wrong-call signal: 有人要求找回误重置的记忆。

### 重置记忆后日志事件照常可用

复制了旧记忆的日志事件在重置记忆后照常可读，也照常通过当前可用性检查，来源显示为已重置。重置是为了重建记忆，抹掉内容靠清除。harness 会把窗口里已知的来源挂到 assistant 片段和工具事件上，并在发出模型请求前检查这些来源；如果旧记忆让这些事件变得不可读或不可用，重置之后重建的窗口会缺掉所有用过记忆的 assistant 输出。

- Rejected: 像清除一样让这些事件不可读，在操作者用重置来擦除隐私内容时更好；像撤回一样让它们仍可读但通不过当前检查，在旧记忆的副本不能流进新记忆时更好。
- Wrong-call signal: 操作者重置记忆后，发现想忘掉的内容仍能从会话日志搜到，或被重建回记忆。

### 模块的 era 写进分区名

存储内核按「模块.era.名称」给每个模块的分区命名。重置记忆时先建好新 era 的空分区，用一次提交切换记忆模块的当前 era，再删除旧 era 的分区；打开存储时会删除不属于当前 era 的分区，中断的重置因此会接着清理。这样重置不必逐键删除，记忆模块的键格式也不用改。

- Rejected: 在每个键前加上 era，再按前缀分批删除旧键，在一个模块重置时必须保留部分数据时更好。
- Wrong-call signal: 打开存储时分区数量或删除旧分区的耗时明显增长。

## Not this

- 会话头记录、fork 和带修订号的会话列表。
- 轮次的开始与结束事件，以及重开时关闭未结束的轮次。
- 对话缓存。
- 把运行状态放进同一存储。
- 只重置会话模块。
- 决定记忆模块的内部模型。
- 读取输入流期间释放写锁。
- 迁移旧格式的数据。
